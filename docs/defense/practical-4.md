# Практична 4 — підготовка до захисту

## З чого складається HTTP-запит? Для чого потрібні метод, заголовки, параметри й тіло?

- **Метод** (GET, POST, …) — яку дію виконати над ресурсом. У проєкті — лише
  `GET /api/random`, бо застосунок тільки читає дані.
- **Заголовки** — метадані запиту/відповіді (наприклад, `Content-Type`,
  очікуваний формат). ZenQuotes повертає JSON без обов'язкових заголовків
  запиту, тому `URLRequest` формується мінімальним.
- **Параметри** — уточнення запиту (query-рядок або шлях). У обраного
  endpoint-у параметрів немає — кожен виклик повертає випадкову цитату.
- **Тіло** (body) — дані, які надсилає клієнт (для POST/PUT). Для `GET`-запиту
  застосунку тіло не потрібне.

## Чим транспортна помилка відрізняється від HTTP-помилки?

- **Транспортна помилка** — запит взагалі не дійшов до сервера чи відповідь не
  повернулася назад: немає мережі, обірваний зв'язок, таймаут. У коді —
  `NetworkError.transport`, виникає, коли сам виклик `client.data(for:)`
  кидає помилку (`catch` навколо нього в `ZenQuotesService`).
- **HTTP-помилка** — сервер відповів, з'єднання відбулося, але код статусу
  поза `200...299` (наприклад, 404, 500). У коді — `NetworkError.badStatus(code:)`.
  Це перевіряється **до** спроби прочитати тіло як успішну відповідь.

## Як працює декодування і що відбудеться при невідповідності формату даних?

`JSONDecoder().decode([ZenQuoteDTO].self, from: data)` зіставляє поля JSON із
властивостями `ZenQuoteDTO` (`q`, `a`) за назвою й типом. Якщо структура не
збігається (відсутнє обов'язкове поле, інший тип значення, взагалі не JSON) —
`decode` кидає `DecodingError`, який `ZenQuotesService` обгортає в
`NetworkError.decoding`. Застосунок не аварійно завершується: `MotivationViewModel`
перехоплює помилку й переводить екран у стан `.failed(...)` з повідомленням і
кнопкою повтору.

## Як організовано асинхронність та оновлення інтерфейсу?

`ZenQuotesService.fetchRandomQuote()` — `async throws`-функція на основі
`URLSession.data(for:)` (структурована конкурентність Swift, без callback-пекла).
`MotivationCardView` викликає її через `.task { await viewModel.load() }`
(один раз при появі) і `Task { await viewModel.load() }` (кнопка «Оновити») —
обидва не блокують головний потік. `MotivationViewModel` позначено `@MainActor`,
тому кожне присвоєння `state = …` виконується на головному акторі, і SwiftUI
безпечно оновлює інтерфейс.

## Для чого потрібна абстракція мережевого сервісу?

`MotivationViewModel` залежить від протоколу `QuoteFetching`, а не від
`ZenQuotesService` напряму — той самий принцип інверсії залежностей, що й для
`DataStoring`/`HapticsProviding` у практичній 2. Завдяки цьому:

- `AppContainer` підміняє реалізацію без зміни `MotivationViewModel`/`MotivationCardView`.
- Негативні сценарії (порожня відповідь, помилка) демонструються керовано —
  `EmptyQuoteService`, `FailingQuoteService` — без вимкнення мережі на пристрої.
- Тести перевіряють `MotivationViewModel` без жодного реального HTTP-виклику.

## Як перевіряти помилки без залежності від випадкових збоїв зовнішнього API?

Два незалежні рівні:

1. **`ZenQuotesServiceTests`** (`SmokeFreeTests/NetworkTests.swift`) підміняють
   `HTTPClient` мок-об'єктом (`MockHTTPClient`), який повертає наперед задані
   `Data`/`HTTPURLResponse` чи кидає помилку, — так перевіряються всі чотири
   випадки (`.transport`, `.badStatus`, `.decoding`, `.empty`) детерміновано,
   без мережі.
2. **`MotivationViewModelTests`** підміняють увесь `QuoteFetching` (`EmptyQuoteService`,
   `FailingQuoteService`, локальний `StubService`) і перевіряють, що ViewModel
   коректно перетворює кожен результат на відповідний `State`.
